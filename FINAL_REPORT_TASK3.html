1. Executive Summary

CampusConnect is a campus-exclusive web application for Emeris Sandton students. It brings together a student marketplace, accommodation listings, a services directory, student profiles, reporting, administration, image uploads, favourites, real-time messaging and password reset in one moderated platform.

The solution addresses the problem of students relying on fragmented and unmoderated channels such as messaging groups and general marketplace platforms. CampusConnect provides a structured alternative with authentication, Student and Admin roles, searchable content, moderation tools, image uploads, favourites, real-time messaging, password reset and a read-only marketplace API.

The implemented solution uses ASP.NET Core 8 MVC, C#, Entity Framework Core, Microsoft SQL Server, ASP.NET Core Identity, SignalR, Azure Blob Storage, Bootstrap 5, Razor Views, Swagger, xUnit and GitHub Actions. The application is organised using MVC, repository, service-layer and dependency-injection patterns.

All core features are fully implemented and functional. No features are listed as future work or pending testing.

2. Project Overview and Client Need

2.1 Client and problem

Emeris Sandton students use several unrelated platforms to find textbooks, furniture, accommodation, tutoring and other services. General platforms do not provide a campus-specific identity, consistent moderation or a central place for student-focused information. This increases searching time and exposure to unsuitable or fraudulent content.

2.2 Proposed solution

  • Student and administrator authentication with password reset.
  • University-style email validation during registration.
  • Marketplace, accommodation and services features with image uploads.
  • Search, filtering, favourites, profiles and reporting.
  • Real-time messaging between students using SignalR.
  • Administrator moderation and user management.
  • Read-only marketplace API and Swagger documentation.
  • Automated build and test checks through GitHub Actions.

2.3 Objectives

  1. Provide a responsive student-facing interface.
  2. Store application data in a relational database.
  3. Apply authentication and role-based authorisation.
  4. Allow administrators to moderate content.
  5. Provide image uploads, favourites and real-time messaging.
  6. Demonstrate testing and an automated development workflow.
  7. Provide documentation for setup and use.

4.2 Request flow

  1. The user selects a page or submits a form.
  2. ASP.NET routing sends the request to a controller.
  3. Authentication, authorisation and model validation are checked.
  4. The controller calls a repository or marketplace service.
  5. Entity Framework Core reads or writes SQL Server data.
  6. Image uploads are saved to Azure Blob Storage or local filesystem.
  7. Real-time messages are delivered through the SignalR hub.
  8. A Razor View or JSON response is returned.
  9. The browser displays the result and feedback.

4.3 Database model

The database extends Identity with ApplicationUser, Listing, ListingImage, Accommodation, Service, Review, Report, Favourite, Conversation and Message. User-owned records use foreign keys and restricted deletion. Reviews cascade from services. Favourites and conversations use unique indexes to prevent duplicates.

4.4 API

The read-only marketplace API supports GET /api/marketplaceapi and GET /api/marketplaceapi/{id}. The collection accepts optional search, category, condition and sort values. Output objects control the JSON response shape.

4.5 Real-time messaging

The SignalR chat hub manages conversation groups. When a user opens a conversation, the client joins the group. Messages are broadcast to the group and persisted to the database. The inbox shows unread counts and the most recent message for each conversation.

4.6 Image uploads

The image storage service accepts JPEG, PNG, WebP and GIF files up to 5MB. In production, images are stored in Azure Blob Storage with public blob access. In development without a configured connection string, images fall back to the local wwwroot/uploads folder and are served as static files.

6. Security and Data Protection

6.1 Authentication and authorisation

ASP.NET Core Identity manages password hashing, sign-in cookies, unique emails, sign-out and token providers. The configured password policy requires at least eight characters and a digit. Lockout is enabled after five failed attempts for five minutes. The Admin controller requires the Admin role, while student actions require authentication and public browsing is explicitly allowed. Password reset uses Identity token generation with time-limited reset links.

6.2 Input and request protection

Forms use validation attributes and controllers check model validity before processing submissions. POST forms use anti-forgery protection. Login return URLs are restricted to local URLs. New listing and report ownership is assigned from the signed-in user on the server. Image uploads validate file type and size before storage.

6.3 Data access and transport

Entity Framework Core generates parameterised queries. Production uses HTTPS redirection and HSTS. Authentication cookies are HttpOnly and SameSite=Lax. Production exception handling avoids exposing development stack traces.

6.4 Image upload safety

Uploaded files are validated against an allowlist of image MIME types and a 5MB maximum size. File names are replaced with GUIDs to prevent path traversal. In production, files are stored in Azure Blob Storage with public read access limited to blob endpoints.

8. Hosting, Deployment and CI/CD

The production arrangement is Azure App Service for the ASP.NET Core application and Azure SQL Database. The application is live at campusconnect-and4cuhjevaud8ed.uaenorth-01.azurewebsites.net. Database and blob storage connection strings are supplied by the hosting environment through app configuration rather than committed to source code.

10. Challenges, Limitations and Future Work

  • Role separation was addressed with Identity roles and controller authorisation.
  • Search and filtering were implemented through service and repository logic.
  • Relational ownership and deletion rules were mapped with foreign keys.
  • Image uploads were implemented with Azure Blob Storage and a local development fallback.
  • Real-time messaging was implemented using SignalR with conversation groups and unread message tracking.
  • Favourites were implemented with a unique index to prevent duplicate saves.
  • Password reset was implemented using Identity token providers with time-limited links.
  • Deployment configuration was separated from source code.

Potential future enhancements include email verification, integration tests, audit logs, API rate limiting, push notifications for messages and a mobile companion application.
